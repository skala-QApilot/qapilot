## 1. 왜 전부 Fail이 나는가? (100% 실패의 심층적/의미론적 원인)

로그를 자세히 뜯어보면, 도구가 요소를 못 찾아서 헤매는 '진짜 이유'가 명확하게 보인다. 이는 단순히 SUT 서버가 꺼져서가 아니라, LLM이 추론한 "기대 결과(Assertion)"와 실제 **"프론트엔드(UI)의 표현 방식"** 간의 거대한 의미론적 괴리(Semantic Gap) 때문이다.

### 🚨 결정적 증거 (로그 발췌)

- `selector="HTTP 401 상태 코드가 반환된다"` (TS-001-TC-06)
    
- `selector="HTTP 404 오류가 발생하고 'Plan not found' 메시지가 반환된다"` (TS-002-TC-02)
    
- `selector="회선이 즉시 'CONFIRMED' 상태로 생성되고 월 요금이 산정된다"` (TS-004-TC-01)
    
- `selector="HTTP 400 Bad Request 에러가 발생하고..."`
    

### 🔍 심층 분석

1. **API 스펙과 UI 렌더링의 혼동 (LLM의 환각)**
    
    - Layer 1B의 `ActionMapperAgent`(LLM)는 백엔드의 도메인 지식이나 요구사항 정의서(PRD)를 바탕으로 검증 스텝을 짰다.
        
    - 하지만 실제 웹 브라우저 화면(UI)에는 "HTTP 404 오류가 발생하고..."라는 텍스트가 날것 그대로 출력되지 않는다. 사용자에게는 "페이지를 찾을 수 없습니다" 형태의 토스트 팝업이나 모달로 렌더링된다. "CONFIRMED 상태"라는 DB 상태값 역시 UI에서는 "가입 완료"라는 뱃지로 표현된다.
        
    - LLM은 API 관점의 기대 결과를 UI DOM의 text로 그대로 입력했다.
        
2. **결과**
    
    - `UITestTool`은 충실하게 브라우저 DOM을 뒤진다. 옵션 A(의미적 체인)를 돌리고, 최후엔 옵션 B(런타임 DOM 스캔 + Fuzzy Match)까지 돌려서 화면의 모든 글자를 긁어왔지만, 브라우저 화면 그 어디에도 "HTTP 400 Bad Request" 라는 텍스트는 없었기 때문에 결국 타임아웃 100% 실패가 나는 것이다.
        
3. **초반 fill 성공 후 실패하는 이유 (TS-001-TC-01)**
    
    - 초반 로그를 보면 `ui_fallback_dom_scan_success`로 "이메일을 입력하세요" 칸을 기적적으로 찾아 fill 동작에 성공한다.
        
    - 하지만 뒤이어 나오는 `steps=4`에서 최종 fail이 떨어진다. 이는 입력을 마친 뒤 제출 버튼을 눌렀을 때, 앞서 우리가 QApilot-UI에서 겪은 500 에러 같은 실제 SUT 백엔드의 오류 때문에 다음 화면으로 넘어가지 못했고, 후속 검증(assert)이 타임아웃된 전형적인 환경/로직 결함 탐지 사례다.
        

> **결론:** 이 100% Fail은 버그가 아니라, **"AI가 짠 비현실적인 UI 시나리오"**와 **"SUT의 실제 백엔드 연동 오류"**를 `UITestTool`이 매우 정확하고 철저하게 걸러낸(Fail 시킨) 결과값이다.

## 2. UITestTool이 너무 무거운 건 아닐까? (LLM 사용 여부)

결론부터 말하자면 `UITestTool`은 LLM을 단 1%도 사용하지 않으며, 컴퓨팅 리소스 관점에서도 전혀 무겁지 않다.

### 💡 파이프라인 내 LLM의 위치 (철저한 분리)

QApilot의 아키텍처 원칙(구현 플랜 §2.3)에 따라, 실행 엔진과 지능은 철저히 분리되어 있다.

- **LLM을 쓰는 곳 (Agent):** 시나리오 생성, 액션 매퍼, 코드 생성, 원인 추론 등 머리를 써야 하는 곳 (Layer 1, Layer 3)
    
- **LLM을 안 쓰는 곳 (Tool):** `UITestTool`, `APITraceTool`, `DBTestTool` 등 팔다리 역할을 하는 곳 (Layer 2)
    

### ⚡ 옵션 A / B의 실제 처리 비용 (성능)

로그에서 10초, 5초씩 걸려서 20초 넘게 걸리는 것은 연산이 무거워서가 아니라, 타임아웃(대기 시간) 때문이다.

1. **옵션 A (의미적 Chain):** Playwright의 C++ 엔진 레벨에서 동작한다. DOM에 요소가 없기 때문에 나타날 때까지 10초, 5초씩 "기다리는(Wait)" 것일 뿐, CPU 연산은 거의 0에 가깝다.
    
2. **옵션 B (DOM Scan + Fuzzy Match):**
    
    - `page.evaluate`: 브라우저 내장 JS 엔진으로 화면의 텍스트를 긁어온다. (10ms 이내)
        
    - `difflib.SequenceMatcher`: 수집된 수십 개의 텍스트 배열과 타겟 텍스트 간의 일치율을 Python 로컬 메모리에서 계산한다. (10ms 이내)
        
    - 즉, 옵션 B 자체의 연산 시간은 0.1초도 안 걸리는 초경량 로직이다.
        

> **🎯 정리:** `UITestTool`은 무거운 AI 도구가 아니다. LLM이 넘겨준 JSON 명령서(`ActionMapping`)를 받아 가장 빠르고 결정적으로 브라우저를 조작하는 순수 Python 자동화 스크립트다. 지금 로그에서 보여지는 "지연"은 화면에 나타나지 않는 요소를 끝까지 찾아내기 위해 도구가 지정된 타임아웃만큼 성실하게 기다려준 시간일 뿐이다.

## 💡 구체적 해결책 (투트랙 전략)

이 100% 실패 문제를 근본적으로 해결하기 위해서는 LLM의 UI 추론 방식 교정과 SUT의 물리적 환경 정상화라는 투트랙(Two-track) 접근이 필요하다. 현재 담당 영역(A: SUT 및 CLI, D: CodeGenerator 및 UITestTool 등)에서 즉시 실행할 수 있는 구체적인 해결책 3가지를 제시한다.

### 1. ActionMapper / ScenarioGenerator 프롬프트 교정 (즉각 적용 가능 - D영역)

가장 큰 원인인 "HTTP 401 반환" 같은 서버 응답을 UI 텍스트로 착각하는 LLM의 환각(Hallucination)을 강력한 프롬프트 제어로 억제해야 한다.

- **수정 대상:** `prompts/action_mapper/system.md` 및 `prompts/scenario_generator/system.md`
    
- **추가할 프롬프트 지침 (예시):**
    
    Markdown
    
    ```
    [CRITICAL: UI 검증(Assert) 작성 규칙]
    - UI 액션(`assert_text`, `assert_visible`)의 `expected` 값에는 **절대** API 응답 코드(예: "HTTP 400", "404 Not Found")나 DB 상태값("CONFIRMED")을 그대로 작성하지 마십시오.
    - 반드시 사용자가 화면에서 실제로 볼 수 있는 **사용자 친화적 자연어 텍스트** (예: "요금제 정보를 찾을 수 없습니다", "가입이 완료되었습니다", "이미 구독 중인 요금제가 있습니다")로 치환하여 작성해야 합니다.
    - UI 요소의 Selector를 지정할 때는 백엔드 변수명이 아닌 화면의 Label이나 Placeholder를 유추하여 작성하십시오.
    ```
    
- **효과:** LLM이 비현실적인 Assertion을 생성하는 것을 막아, 앞선 로그처럼 타임아웃이 날 때까지 헛도는 현상을 80% 이상 제거할 수 있다.
    

### 2. SUT(mini-bss-lite) 환경변수 및 의존성 정상화 (즉각 적용 가능 - A영역)

첫 번째 스텝(fill)은 성공했는데 두 번째 스텝으로 넘어가지 못하는 이유는 십중팔구 SUT(테스트 대상 시스템) 내부의 통신 에러(500 Internal Server Error) 때문이다.

- **수정 대상:** `mini-bss-lite/tests/test_ground_truth.py` 및 SUT 도커 환경
    
- **구체적 조치:**
    
    1. `test_ground_truth.py` 내의 하드코딩된 `BASE_URL(http://localhost:8000)`과 `CONTRACTS_URL(http://contracts-service:8001)`을 `os.getenv`로 감싸 로컬과 도커 내부 양쪽에서 유연하게 통신할 수 있도록 리팩토링한다.
        
    2. `mini-bss-lite`의 백엔드와 프론트엔드가 정확한 포트와 CORS 설정으로 통신하고 있는지(실제 화면에서 500 에러가 안 나도록) 점검하고 환경변수(`.env`)를 교정한다.
        
- **효과:** SUT 자체가 정상적으로 동작해야 QApilot의 UI Test Tool도 다음 화면으로 넘어가며 제대로 된 검증을 수행할 수 있다.
    

### 3. 프론트엔드 DOM 스캔 결과 인덱싱 (근본적 아키텍처 해결 - C영역 협업 필요)

장기적으로는 LLM이 UI 텍스트를 "추론"하게 둬서는 안 된다. (문서 `docs/frontend-dom-scan-gap.md`에 명시된 근본 원인)

- **수정 대상:** C 담당의 `CodebaseScannerTool`
    
- **구체적 조치:** 백엔드 API 스캔뿐만 아니라, 프론트엔드(React/Vue) 코드를 정적 분석하여 `<button>`, `<input>`, `data-testid` 등에 하드코딩된 텍스트와 라벨을 추출해 `.qapilot/codebase-index/frontend.json`으로 저장해야 한다.
    
- **효과:** 이 인덱스를 ActionMapper에게 쥐여주면, LLM은 100% 실제 존재하는 DOM 텍스트만 사용하여 시나리오를 매핑하므로 적중률이 비약적으로 상승한다.

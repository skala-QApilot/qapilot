# RL 효과 측정 — 영역-우선순위 정책 오프라인 평가 (OPE) 결과

> 재현: `python scripts/rl_offline_eval.py` (DATABASE_URL 설정 필요)
> 측정일 기준 데이터: 라이브 `qapilot` DB, defects 보유 런 36개(분석가능 34 폴드 / 서비스 3).

---

## 1. 무엇을 측정했나 (그리고 무엇을 측정하지 않았나)

**측정한 것 (정직한 범위)** — RL 정책(컨텍스트 밴딧)의 **영역 우선순위 품질**:

> *"제한된 '시나리오 예산' 하에서, 밴딧이 과거 런으로 학습한 도메인 영역 우선순위로
> 테스트 순서를 정하면 — 무작위(학습 없음)보다 제품결함을 더 일찍/더 많이 잡는가?"*

이것은 실측 로그에 대한 **반사실(counterfactual) 평가**다. 표준 오프라인 정책 평가(OPE).

**측정하지 않은 것 (조작 방지를 위해 명시)**:
- ❌ "RL 이 생성 LLM 을 더 좋게 만들어 결함을 더 잡는다"는 **엔드투엔드** 주장. 그건 전체
  파이프라인(생성→실행→cross-check)을 힌트 ON/OFF 로 **다회 실행** + **결함주입 ground-truth**
  가 필요하며, 본 평가 범위 밖. (§5 에 실행 방법 명세)
- ❌ **cross-domain 전이**. train/test 는 **같은 SUT 의 다른 런**(within-SUT 학습). 도메인 간
  일반화는 미검증.

---

## 2. 실험 설계 (Leave-One-Run-Out 교차검증)

```
서비스(SUT)별로:
  각 런을 한 번씩 test 로:
    train = 그 서비스의 나머지 런들 → 밴딧 학습(영역별 성공/실패 누적)
    test  = 남긴 런
    · 밴딧: 영역을 사후평균 내림차순으로 정렬(결정적 — 학습지식 자체를 평가)
    · 예산 f 만큼 시나리오를 그 순서로 소비 → 잡은 제품결함 비율(lift curve)
비교군:
    무작위(베이스라인, 학습 없음, 몬테카를로 500회 평균)
    오라클(상한, test 런의 실제 영역 수율 순)
통계: 폴드별 리프트(밴딧−무작위)@50% 의 부트스트랩 95% CI (n_boot=4000)
```
- **success = 시나리오가 확정 제품결함을 잡음** (오탐/환경결함/보류 제외, `reward.py` 기준).
- 평가 지표 = **예산 f 를 썼을 때 포착한 제품결함 비율** (= 운영상 "예산 한정 결함 포착력").

## 3. 결과

### 3.1 전체 폴드 (34) — 단, degenerate 런 포함이라 과대평가

| 예산 | 무작위 | RL(밴딧) | 오라클 | RL 리프트 |
|---|---|---|---|---|
| 25% | 26.0% | 59.3% | 66.7% | **+33.2%p** |
| 50% | 50.5% | 74.1% | 83.4% | **+23.6%p** |
| 75% | 74.4% | 85.1% | 93.0% | +10.6%p |
| AULC | 0.502 | 0.703 | 0.771 | +0.200 |

50% 예산 리프트 95% CI: **[+14.2%p, +32.4%p]** (유의).

### 3.2 서비스별 — **이야기가 갈린다 (정직한 핵심)**

| service | folds | 평균 결함수 D | 무작위 | RL | 오라클 | 리프트 |
|---|---|---|---|---|---|---|
| 4699ddb4 | 13 | 18.0 | 0.50 | 0.49 | 0.65 | **−0.01 (효과 없음)** |
| 6aed684e | 8 | 10.8 | 0.51 | 0.72 | 0.87 | **+0.22 (확실한 효과)** |
| 9f2a7d4f | 13 | **1.0** | 0.51 | 1.00 | 1.00 | +0.49 (saturated) |

- **9f2a7d4f**: 런당 결함이 **1건뿐** → 밴딧이 그 영역을 학습해 자명하게 포착(1.00). 효과는
  실재하나 **포화(saturated)** 라 전체 평균을 부풀린다.
- **4699ddb4**: 결함이 영역에 **고르게** 퍼짐(대부분 영역이 고수율) → **우선순위가 의미 없어
  RL ≈ 무작위**. 정직한 음성 결과.
- **6aed684e**: 결함이 영역별로 **불균등** → **RL 이 무작위 대비 +22%p**. RL 이 빛나는 전형.

### 3.3 비-degenerate 부분집합 (D≥3) — **방어 가능한 헤드라인**

우선순위가 *실제로 의미 있는* 런(결함 1~2건 포화 런 제외, 18 폴드):

| 예산 50% | 값 |
|---|---|
| 무작위 베이스라인 | 50.1% |
| **RL(밴딧)** | **62.1%** |
| 오라클 상한 | 68.6% |
| **리프트** | **+12.0%p** |
| 95% CI (부트스트랩) | **[+6.2%p, +19.2%p]** → 유의 (0 제외) |
| 오라클 헤드룸 회수 | **65%** |

## 4. 결론 (한 문장씩)

- **결함이 영역별로 불균등한 현실적 상황에서, RL 밴딧은 50% 테스트 예산으로 무작위 대비
  제품결함을 약 +12%p 더 포착한다** (95% CI [+6, +19], 통계적으로 유의). 이는 "완벽한
  사전지식(오라클)"이 가진 개선폭의 **약 65%를 회수**한 값이다.
- **결함이 거의 모든 영역에 고르게 퍼지면(4699ddb4) 효과가 없다** — 우선순위로 얻을 게
  없는 게 당연하므로, 이는 방법의 한계가 아니라 **데이터 특성**이다.
- 전체 평균 +23.6%p 는 결함 1건짜리 포화 런에 끌려간 **과대** 수치이므로, **방어 가능한
  대표값은 +12%p(D≥3)** 로 보고한다. ← 정직한 권장 인용값.

## 5. 진짜 엔드투엔드 A/B 를 돌리는 법 (아직 안 함 — 명세만)

위는 *영역 우선순위*의 가치다. *"RL 힌트를 생성 프롬프트에 넣으면 결함을 더 잡나"* 의
인과 증명은 아래가 필요하다 (라이브 스택 + 시간 + 결함주입 SUT):

1. **SUT**: `mini-bss-lite` 에 알려진 결함을 주입(ground-truth, `faults/BUG-*.yaml`).
2. **두 팔(arm)**:
   - **OFF**: 현행 생성(`_ts_generate_prd_only` 그대로).
   - **ON**: 생성 직전 `RLService.plan(...).as_prompt_hints()` 를 프롬프트에 주입.
3. **반복**: 각 팔을 **여러 시드로 N회** 전체 파이프라인 실행(생성→실행→cross-check).
4. **지표(주입결함 대비)**: 결함 검출 recall, 결함당 비용(토큰/시간), 시나리오 다양성,
   pass@1.  팔 간 차이를 **부트스트랩/순열검정**으로 유의성 판정.
5. **주의**: 보상에 쓴 신호(cross-check)와 평가 신호(주입 ground-truth)를 **분리**해야
   순환논증을 피한다.

이 측정 트랙(`scripts/metrics/`, 결함주입)과 결합하면 본 OPE 의 "우선순위 가치"를
"실제 결함 검출 향상"으로 확정할 수 있다.

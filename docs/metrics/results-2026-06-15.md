**측정 인프라는 정상 작동**하며, 결과는 QApilot의 실제 약점을 드러낸다: **생성된 테스트의 오라클(then 기대값) 품질이 낮아, clean SUT에서 대량 오탐이 발생하고 그 노이즈가 결함 검출을 가린다.** 결함 주입 자체는 SUT에서 정상 동작하므로, 이는 측정 오류가 아니라 **유효한 1차 측정 결과**다.

## 핵심 발견 (근거 포함)

### 1. 검출이 되는 경우는 확실히 된다 — 오라클이 정확할 때 (RULE-001)
TS-001-TC-05는 "미성년 보호자 미동의 → 거부" 케이스. 오라클이 응답 메시지(보호자 동의 문구)를 정확히 검증.
- clean: predicate **충족 → PASS**
- RULE-001 ON: 실제 201(우회) → "기대 4xx, 실제 201" **→ FAIL = 정확 검출**. 3런 모두 일관(pass^k).
→ **파이프라인의 결함 검출 능력 자체는 유효**하다.

### 2. 대량 오탐의 정체 = 생성된 테스트의 오라클 결함 (제품 결함 아님)
clean SUT인데 49~51 TC가 fail + PRODUCT로 분류. 표본 summary:
- `TS-001-TC-03: 기대 status 400~499 — 실제 201` (clean에선 201이 정답인데 테스트가 4xx 기대)
- `TS-002-TC-02/03: then 코드 미명시, LLM 추정 [400]` → **then에 기대 status가 없어 LLM이 추측 → 빗나감 → 오탐**
→ 근본 원인: **생성된 시나리오의 `then`에 기대 상태코드가 자주 누락/부정확** → cross-check가 mismatch로 오판.

### 3. 그 오탐이 결함 검출을 가린다 (RULE-002/003/004/API-001 미검출)
결함이 영향을 주는 TC가 clean에서 **이미 오탐으로 fail** 중이면, 결함을 켜도 verdict 변화(delta)가 없어 "신규 검출"로 잡히지 않는다. SUT 결함은 정상 주입(sanity 통과)이나, 약한 오라클 때문에 신호가 노이즈에 묻힘.

### 4. 결정분류(②)의 PRODUCT 과대귀속
clean의 모든 fail은 SUT가 정상이므로 **TEST_DEFECT여야** 하는데, 50/58이 PRODUCT_DEFECT_CANDIDATE로 분류됨. `_classify_failure`가 테스트측 결함(오라클 오류)을 제품 결함으로 과대 귀속.

## 측정 불가 항목 — 데이터 갭 (다음 차수에 보완)
- **①장애유형**: `error_code`가 106/121에서 빈값 → `_infer_defect_type` None. 산출하려면 cross_check가 error_code를 채우거나, root_cause category로 ① 유도 필요.
- **원인 추론 위치(Top-N)**: root_cause 후보의 `file_path`가 전부 None — 위치는 `fix_recommender` 출력(file_path 존재)에 있음. 측정 스크립트가 **fix_results를 아티팩트에 함께 저장**하도록 보완하면 재실행 없이도(다음 런부터) 측정 가능.

## 권장 (우선순위)
1. **[최우선] 시나리오 `then` 오라클 강화** — 기대 상태코드/응답을 명시 생성하도록 scenario_gen 개선. 이것이 테스트코드정확도·오탐·검출을 동시에 끌어올리는 단일 레버.
2. **결정분류 재보정** — clean fail을 PRODUCT로 과대귀속하지 않도록 `_classify_failure` 임계/규칙 점검(오라클 미명시 fail은 TEST_DEFECT로).
3. **측정 스크립트 보완** — 아티팩트에 `fix_results` 저장(원인 위치 측정), 검출 기준선을 clean **합집합**으로(노이즈 제거). golden `then`(명시 status 보유)을 보조 오라클로 대조하는 옵션 추가.
4. **2차 측정** — 1~3 반영 후 재실행(저장 아티팩트 재채점은 즉시 가능, 신규 데이터는 재런).

## 결론
- 측정 파이프라인(SUT 토글·게이트웨이·DB 로컬 관측·in-memory 수집·채점)은 **end-to-end 검증 완료**.
- 1차 수치: **테스트코드정확도 51%, 유효판정율 93%, 검출 1/5(오라클 강건한 케이스만), 분류②정밀도 낮음**. ①·원인은 데이터 갭으로 보류.
- 가장 큰 발견은 **오라클 생성 품질**이 병목이라는 점 — 목표치(90%) 도달의 핵심 선결과제.

## 최종 결론 — develop 5개 지표 완전판 (재실행 없이 저장 아티팩트로 산출)

> 본 수치는 **develop 버전 QApilot 거동**이다. 측정값을 생성하는 파이프라인 로직
> (`orchestrator/pipeline.py`·`agents/*`·`tools/*`)은 develop과 동일(미변경). 우리가 고친
> 부분은 ① SUT 테스트 환경(seed·compose·gateway·sut-db-agent) ② ground truth(golden·faults)
> ③ 측정 스크립트뿐이며, 제품 측정 거동에 영향이 없다. **즉 아래 표는 develop을 그대로 측정한 값이고,
> develop 재실행이 필요 없다.**

| 지표 | 현재 측정값 (develop, 본 SUT 1차) | 성격 | 비고 |
|---|---|---|---|
| **유효 판정율** | **~88%** | 완전성 | 결론(P/F) 도달율 높음 — 정확성과 분리 |
| **테스트 코드 정확도** | **51%** | 정확성 | clean에서 49% TC가 fail (생성 오라클 약함) |
| **결함 검출** | **Recall 20% (1/5)** · **Precision ~2%** | 정확성 | RULE-001만 검출. 오탐 ~50건/런 중 진짜 1건 |
| **장애 분류** | **②결정분류만 산출** (검출 1건 ②=PRODUCT 정분류) | 정확성 | **①장애유형은 develop이 미산출**(error_code 빈값). clean 50건도 PRODUCT → 변별력 없음 |
| **원인 추론** | **위치 자동채점 불가** / 의미 검출 1건 부분일치 | 정확성 | root_cause 후보의 `file_path`를 develop이 미산출. 검출 1건 cause="signup 검증 누락"(영역 일치, 보호자동의 특정 못함) |

### 정정 사항
- 앞 절의 "측정 불가"는 부정확한 표현이었다. **데이터는 저장돼 있으며**, ①장애유형·원인 위치는 "측정 실패"가 아니라 **develop 파이프라인이 해당 필드를 출력하지 않는 것** 자체가 결과다.
- `metrics_report.json`의 검출율(0.67)은 단일 clean 런 기준 노이즈 오집계 — 위 표(clean **합집합** 기준)가 정정 honest 수치.

### 측정으로 드러난 develop의 현 상태 (객관 관찰)
1. **유효 판정율은 높으나(88%) 정확성이 낮다** — 결론은 잘 내지만 그 결론이 자주 틀림.
2. **병목 = 생성 오라클 품질**: `then`에 기대 status 미명시 → cross-check가 LLM 추정으로 빗나감 → clean 오탐 ~50건 → 결함 검출을 가림(Recall 20%, Precision 2%).
3. **①장애유형·원인 위치는 develop 산출 항목이 아님** — 측정하려면 제품 확장 필요(별도 의사결정).
4. SUT 결함 토글은 전 구성 정상(sanity 통과) — 낮은 수치는 측정 결함이 아니라 develop의 실제 성능.

> 본 측정은 develop의 현 성능을 있는 그대로 보여주는 1차 결과다. 개선 방향(오라클 강화 등)은
> 제품 변경 사항이므로 측정 범위 밖이며, 팀 의사결정 후 별도 차수로 재측정한다.

## 부록 — A+B+C 수정 + gpt-5.4-mini 재생성 실험 결과 (2026-06-16): **역효과**

생성 오라클 품질을 높이려 4가지를 적용·재생성·재측정한 결과, **지표가 오히려 악화**되어 v1으로 복원했다. 정직한 기록.

### 적용한 수정 (브랜치에 커밋됨)
- **(A) 분류기**: api-mode 추정오라클 fail → TEST_DEFECT (커밋 `2c88355`). — **타당, 유지 권장.**
- **(B) 프롬프트**: then 명시 HTTP status 필수 + observe 절제 (커밋 `0e74f9f`).
- **(C) ①장애유형**: root_cause defect_type(상태코드+도메인규칙 신호) 산출 (커밋 `0e74f9f`).
- **모델**: gpt-4o(deep)/gpt-4o-mini → **gpt-5.4-mini-2026-03-17 통일**.

### 재생성 + 재측정 결과 (clean, v2 vs v1)
| | v1 (gpt-4o, 기존) | v2 (gpt-5.4-mini + A·B·C) |
|---|---|---|
| 생성 TC 수 | 121 | **240** (약 2배) |
| 테스트 코드 정확도 | 52.9% | **26.7%** ↓ |
| 유효 판정율 | 93.4% | **67.5%** ↓ |
| PRODUCT 오탐(clean) | 49 | **98** ↑ |

### 근본 원인 — UI-mode DOM grounding 격차 (오라클 문제 아님)
- v2 clean fail 176건 중 **UI-mode가 152건**(api-mode 24). UI-mode 152 = PRODUCT 오탐 86 + 셀렉터 실패 26 + 텍스트 assert 실패 40.
- **gpt-5.4-mini는 더 상세한 UI 테스트를 대량 생성**했는데(예: `order-detail-status` 요소 기대), **실제 SUT 프론트엔드에 그 testid/요소가 없어** UI 실행이 무더기로 실패 → 오탐 폭증.
- 즉 (B)의 API 오라클 명시화는 작동했으나(then 12%→100% 명시), **지배적 실패 모드는 UI-mode이고 그건 오라클이 아니라 프론트엔드 DOM grounding(frontend-dom.json) 품질 문제**다. 더 좋은 모델이 더 많은 UI 테스트를 만들수록 grounding 격차가 커져 악화됐다.
- gpt-4o가 "덜 상세"해서 UI 테스트가 적었던 것이 역설적으로 v1 지표가 나았던 이유.

### 결론·권고
- **develop 성능의 정직한 수치는 v1**(정확도 52.9%, 유효 93.4%, 검출 1/5, 오탐 49).
- (A) 분류기 수정은 타당하니 유지. (B)/(C)/모델은 **UI-mode DOM grounding을 먼저 해결하지 않으면 효과 없음**(오히려 역효과).
- 진짜 레버 = **프론트엔드 DOM 인덱싱 품질**(생성 UI 셀렉터가 실제 DOM에 실재하도록) 또는 **api-mode 한정 측정**(오라클 명시화 + A가 유효한 영역).

| 지표 | 1차 | 2차(예측) | 바뀌나 | 왜 |

## 1. 장애 분류는 ① + ②인데, develop은 ②만 했다 — 그래서 ①을 추가했다

장애 분류 정확도는 **두 축**을 모두 맞혀야 한다.

- **①장애유형** = *무슨 종류*의 결함인가 (DOMAIN_RULE / API_ERROR / DATA_MISMATCH / INFRA / UI_ERROR).
- **②결정분류** = *누구 책임*인가 (제품 결함 후보 / 테스트 결함 / 환경 문제).

1차에서 보니 **develop은 ②결정분류만 산출**했다(②=100%). 반면 **①장애유형은 아예 안 나오거나(None) status로만 추정해 API_ERROR로 뭉개져** 0%였다. 그래서 2차의 핵심 작업은 **"①장애유형을 제대로 산출·분류하게 만드는 것"** 이다.

> 즉 흐름은: *원래 장애 분류 = ① + ② 둘 다 필요 → develop은 ②만 했다 → 2차에서 ①을 추가했다 → 이제 측정한다.*

## 2. 1차 이후 무엇을 수정/추가했나

> **원칙은 1차와 동일**: QApilot의 *verdict·검출* 같은 "측정 대상 핵심 로직"은 건드리지 않는다.
> 2차에서 추가한 것은 **이미 시스템 안에 있던 분석 결과(원인 추론)에서 ①장애유형을 끌어내 노출**하는 부분이고,
> 이건 검출/판정 수치에 영향을 주지 않는다(§3에서 증명).

### (가) ①장애유형을 LLM 구조화 분류로 산출 — *일반적*으로
- 원인 추론 에이전트(`root_cause_agent`)가 원인을 분석하면서 **결함의 종류(defect_type) 5종 중 하나**를 함께 출력하도록 했다.
- **특정 도메인 단어(미성년·요금제 등)로 하드코딩하지 않는다.** 결함의 *본질*로 판단하게 프롬프트로 안내 → 어떤 SUT에도 동작.
- 산출된 ①장애유형은 결함 기록(`defects.defect_type`, V19 컬럼)에 저장된다. 제품 결함일 때만 채우고, 단서 없으면 비운다(임의 기본값으로 정확도를 부풀리지 않음).

### (나) 원인 LLM에 "기대 동작(규칙)"을 주입 — ①의 정확도를 끌어올린 핵심
- 1차에서 ①이 0%였던 진짜 이유: 결함이 **"상태코드 차이"(예: 기대 400, 실제 201)** 라는 *증상*으로만 보여, LLM이 이를 **API_ERROR**로 분류했다. "보호자 동의 없이 가입을 막아야 한다"는 **규칙 위반(DOMAIN_RULE)** 이라는 본질을 몰랐던 것.
- 그래서 원인 추론 단계에 **그 테스트가 기대한 정상 동작(시나리오의 `then` 절 = 명세된 규칙)** 을 입력으로 넣어줬다(`expected_behavior`).
- 프롬프트도 *"기대가 조건부 거부/허용/제한인데 SUT가 어겼으면, 증상이 상태코드 차이로 보여도 본질은 DOMAIN_RULE"* 이라고 안내.
- **검증(RULE-001 SUT 스모크)**: defect_type이 `DOMAIN_RULE`로 나오는 케이스가 **0건 → 32건**으로 바뀜(증상이 아니라 어긴 규칙으로 분류 시작). 같은 컨텍스트가 원인 *설명(cause)* 도 규칙 위반을 짚게 해 **원인 의미 일치**도 개선될 것으로 기대.

### (다) 시도했다가 되돌린 것 — *정직 기록*
2차는 "검출까지 끌어올리려" 더 과감한 시도도 했으나, **검출을 깨거나 일반성을 해쳐 되돌렸다.**

- **(A) api-mode 추정오라클 fail을 TEST_DEFECT로 재분류** → "기대 4xx인데 결함이 잘못 성공(201)"을 테스트 오류로 본 것. 그런데 이 신호는 *clean의 오기입* 과 *결함의 진짜 증상* 을 구분하지 못해, **RULE-001 검출까지 TEST_DEFECT로 죽였다.** clean-union 비교(측정 도구)만이 둘을 가른다 → **전면 revert.**
- **시나리오 재생성(gpt-5.4-mini)으로 오라클 강화** → 오라클 명시는 늘었으나 **TC 240개 양산 + UI-mode 환각 단언**으로 오탐이 49→98로 폭발 → **v1 시나리오 복원.**
- **C의 SUT-전용 정규식(미성년/요금제 키워드)** → 우리 측정 대상에만 맞춘 분류라 **일반성 위반 → revert**, (가)의 LLM 구조화 분류로 대체.

### (라) 모델 통일 — *혼입변수로 명시*
- 1차: `gpt-4o-mini`(일반) / `gpt-4o`(deep). 2차: **`gpt-5.4-mini`로 통일**(양쪽).
- 따라서 2차 재측정은 1차와 **①코드(①장애유형 산출) ②모델** 두 가지가 동시에 다르다. api-mode verdict는 LLM을 안 거치므로 **검출/Precision은 모델 영향 없음**(예측 유지). 단 UI-mode의 LLM 판정 수치는 모델로 *약간 흔들릴 수 있음*(개선 보장 아님).

## 3. 전수 점검 — 왜 검출·Precision·정확도는 "그대로"인가 (정직)

재측정 전, "검출 1/5는 그대로인가? 정확도/Precision도?"를 근거로 검증했다.

**검출·Precision·정확도·유효판정율은 모두 `clean 오탐`이 좌우한다.** 1차 clean에서 결함도 없는데 FAIL이 난 57건(오탐)을 정체별로 분류하면:

| 오탐 유형 | 건수 | 정체 | 고치려면 |
|---|---|---|---|
| body predicate 과엄격 | 16 | `then`에 없는 응답 본문(`$.detail`)까지 단언해 실패 | 시나리오 **재생성** |
| 4xx 음성오라클 오류 | 11 | "기대 4xx, 실제 201" — 테스트 데이터가 거부조건을 못 깨움 | **재생성** |
| UI assertion | 14 | UI-mode 요소/DOM 단언이 clean에서도 실패 | **재생성/DOM 보강** |
| 404 매핑 | 16 | 존재하지 않는 엔드포인트 호출 | **재생성** |

**핵심 인과**: 결함이 노리는 엔드포인트의 TC가 *clean에서 이미 오탐으로 FAIL* 이면 → 결함을 켜도 **새 FAIL이 안 생겨** 검출이 누락된다(검출 1/5의 근본 원인). 그리고 이 오탐들은 **전부 시나리오/TC 생성 품질** 문제다.

→ 그런데 2차는 **시나리오를 재생성하지 않고 v1을 복원**했고(재생성은 역효과), 측정은 `command=test`(생성 없이 실행)다. 따라서 **생성물이 1차와 동일 → 이 네 지표는 구조적으로 불변.**

> **왜 verdict 로직으로 오탐을 억누르지 않나?** 그건 *측정 대상 거동을 바꿔 지표를 조작*하는 것이라 측정 원칙에 어긋난다. 검출을 진짜로 끌어올리려면 **"재생성을 망치지 않고 오라클 품질을 올리는"** 더 깊은 작업(UI-mode DOM grounding 등)이 필요하며, 이는 2차 범위를 넘는 별도 과제다.

## 4. 결과 (develop+2차 개선, 본 SUT) — 정식 N=1 재측정은 승인 후 실행

> 현재 확보된 증거: **①장애유형 스모크(RULE-001 SUT)에서 DOMAIN_RULE 분류 0→32건**.
> 아래 표의 1차는 실측(2026-06-16, N=1, gpt-4o-mini), 2차는 **전수 점검 기반 예측 + ① 스모크 검증**.
> 정식 6구성×N=1 재측정으로 2차 실측값을 채울 예정(1차와 동일 조건 비교).

| 지표 | 1차 실측 | 2차 | 근거 |
|---|---|---|---|
| 유효 판정율 | 93.4% | ≈ 동일 예측 | verdict 로직·생성물 무변경 |
| 테스트 코드 정확도 | 52.9% (오라클명시 56.6%) | ≈ 동일 예측 | 시나리오 재생성 안 함 |
| 결함 검출 | Recall 20%(1/5) · Precision ~2% | ≈ 동일 예측 | clean 오탐(생성 품질) 불변 |
| 장애 분류 ②결정분류 | 100% | ≈ 동일 예측 | 원래 정상 |
| **장애 분류 ①장애유형** | **0%** | **유의미 개선**(스모크 검증) | 규칙-컨텍스트 주입 → DOMAIN_RULE 정확 분류 |
| 원인 추론 위치 (Top-N/MRR) | 100% / 1.0 | ≈ 동일 예측 | fix 후보 로직 무변경 |
| **원인 추론 의미** | **0%** | **개선 기대** | 원인 LLM이 규칙(then)을 받아 "동의 우회"를 짚음 |

### 해석 (정직)
- **2차의 진짜 성과는 "장애 분류 ①장애유형"이다.** develop이 못 내던 ①을, 특정 SUT에 의존하지 않는 *일반적 LLM 구조화 분류 + 규칙 컨텍스트 주입* 으로 산출·정확분류하게 만들었다(0→유의미). 이는 장애 분류 정확도(①∧②)를 0%에서 끌어올리는 직접적 개선이다.
- **원인 추론 "의미"도 같은 주입으로 개선이 기대된다.** 1차에서 cause("입력검증 누락")가 정답("보호자 동의 우회")과 어긋났는데, 이제 원인 LLM이 규칙(`then`)을 보므로 설명이 규칙 위반을 짚을 가능성이 커졌다.
- **검출·Precision·정확도는 정직하게 "그대로"다.** 이를 올리려면 verdict 조작(원칙 위반)이 아니라 **시나리오 생성 품질**(오라클·UI grounding)을 재생성을 망치지 않고 개선하는 별도 과제가 선결되어야 한다. 2차는 그 경계를 넘지 않았다.
- **혼입변수(모델) 명시**: 2차는 모델도 gpt-5.4-mini로 바뀌어, UI-mode LLM 판정 수치가 약간 흔들릴 수 있다(개선 보장 아님). api-mode 중심의 검출 수치는 모델과 무관.

(WBS KPI 매핑: 장애 분류↔Cross-check/원인 분류 정확도. 검출력 개선은 생성 품질 과제로 별도 트랙.
시나리오 생성 정확도는 다른 팀원 담당 지표라 본 문서 범위 밖.)

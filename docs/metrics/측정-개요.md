# QApilot 성능 측정 — 개요 (한눈에)

> develop 버전 QApilot의 성능을, 통제된 로컬 SUT(mini-bss-lite)에서 **재현 가능하고 정답
> 기반**으로 측정한다. 본 문서는 *무엇을·왜·어떻게* 측정하는지를 완벽 정리한다.
> 상세 설계는 `measurement-design.md`, 결과는 `results-2026-06-15.md`.
> 각 레포 브랜치 `feat/juhwan/metrics-measurement`에서 진행하였다.

## 1. 무엇을 측정하나 — 5개 지표와 그 의미

| 지표 | 한 줄 의미 | 성격 | 왜 보는가 |
|---|---|---|---|
| **유효 판정율** | 시스템이 "맞다/틀리다"를 분명히 결론낸 비율 (보류·미검증 제외) | 완전성 | 결론을 내긴 하는가? |
| **테스트 코드 정확도** | 생성한 테스트가 정상 SUT에서 **올바른 verdict**(통과)를 내는 비율 | 정확성 | 그 결론이 맞는가? |
| **결함 검출 정확도** | 주입한 결함을 잡아내는 **Recall / Precision** | 정확성 | 실제 버그를 잡는가? |
| **장애 분류 정확도** | 검출 결함의 분류(①장애유형 + ②결정분류)가 정답과 맞는 비율 | 정확성 | 무슨/누구 책임 결함인지 맞히는가? |
| **원인 추론 정확도** | 추론한 원인이 정답과 맞는지 (위치 Top-N + 의미) | 정확성 | 어디가 왜 잘못됐는지 맞히는가? |

### 왜 "5개"로 바꿨나 — 이전 틀(테스트 코드 정확도 → 유효 판정율 + 장애 분류/원인 추론)의 문제

이전엔 지표를 2~3개로 뭉뚱그렸지만, 측정해보니 **서로 다른 것이 섞여 있어** 분리가 필요했다.

1. **완전성과 정확성은 직교한다.** "결론을 냈다(유효 판정율)"와 "그 결론이 맞다(정확성)"는 별개다.
   시스템이 결론은 잘 내도(완전성 높음) 그 결론이 자주 틀릴 수 있다. 그래서
   **유효 판정율(완전성)** 과 **테스트 코드 정확도(정확성)** 를 **독립 지표**로 분리했다.
2. **검출은 분류·원인의 전제다.** 결함을 *검출*하지 못하면 분류도 원인 추론도 의미가 없다.
   그래서 **결함 검출(Recall/Precision)** 을 독립 지표로 명시했다.
3. **분류·원인은 더 정밀하게.** 장애 분류는 ①장애유형(무슨 종류) ∧ ②결정분류(누구 책임)로,
   원인 추론은 위치(Top-N) + 의미(LLM 판정)로 쪼개 정답과 정확히 대조한다.

→ 결과적으로 **유효 판정율 · 테스트 코드 정확도 · 결함 검출 · 장애 분류 · 원인 추론** 5개가 됐다.

### (+) 생성 단계 지표 — 시나리오 생성 정확도 (실행 5지표와 직교)

위 5개는 *테스트를 실행한 결과*를 본다. 그 전에 **QApilot이 시나리오·테스트케이스를 제대로
"생성"했는가**(정답 golden 대비)도 측정해야 한다. 이는 WBS의 **「시나리오 생성 정확도」** KPI이자
**RTM(요구사항 추적) 커버리지**다. golden(114 TC / 30 TS / 29 FR)을 정답으로 한다.

| 지표 | 의미 | 산식 |
|---|---|---|
| **TC Recall** | 정답 케이스를 얼마나 빠짐없이 커버하나 | 매칭 TC / golden TC(114) |
| **TC Precision** | 생성한 케이스 중 정답에 대응하는 비율(잉여·중복·환각 역지표) | 매칭 TC / 생성 TC |
| **TS Recall / Precision** | 시나리오(요구사항 묶음) 단위 동일 | 매칭 TS / golden TS(30) · 생성 TS |
| **Requirement Coverage** | 모든 FR이 최소 1개 시나리오로 커버되나 | 커버된 FR / 전체 FR(29) |

> 예: TC Recall 104/114=91.2%, TC Precision 104/228=45.6%, TS Recall 19/30=63.3%,
> TS Precision 19/29=65.5%, Requirement Coverage 29/29=100%.
> (Recall 높고 Precision 낮음 = "정답은 거의 다 만들되, 그만큼 잉여도 많이 만든다"를 뜻함.)

## 2. 측정을 위해 무엇을 수정/추가했나

> **원칙: QApilot의 "측정 대상 로직"(verdict·분류·검출·원인 추론)은 한 줄도 바꾸지 않았다.**
> 즉 측정값은 **develop 거동 그대로**다. 바꾼 것은 ①테스트 대상(SUT) 환경 ②정답지(ground truth)
> ③측정 도구, 그리고 ④"이미 시스템 안에 있던 신호를 측정 가능하게 노출"하는 최소 계측뿐이다.

### (A) SUT 쪽 — 테스트 대상 환경 (mini-bss-lite)
- **결함 토글 배선**: `ENABLED_FAULTS` 를 backend·contracts 양쪽에 주입(기존 일부 누락). 결함 ON/OFF로 측정.
- **fault-triggering seed**: demo 계정에 `birth_date` 부여 + 미성년 계정 추가 → 미성년/성인 검증 결함이 실제로 발동.
- **결함 유효화**: RULE-003(위약금 계산 순서) 등 ground truth로 쓸 수 있게 일부 주입 결함 수정.
- **단일 origin 게이트웨이(nginx)**: 배포 ingress와 동형으로 `/api`→backend·`/`→frontend 라우팅 → QApilot이 한 URL(8090)로 UI/API 모드 모두 테스트.
- **로컬 DB 검사 에이전트(sut-db-agent)**: DB cross-check가 **로컬 SUT DB**(8091)를 관측하도록(기존엔 배포 SUT를 봄 → 오염).
- **golden**: 정답 시나리오 114케이스 전수 검증 + 오라클 1건 정정.

### (B) QApilot 쪽 — 측정 노출용 최소 계측 (거동 무변경)
- **`_api_error_code`**(pipeline): api-mode 실패의 `error_code`를 관측 status(`API_4xx`/`INFRA_5xx`)로 복원.
  기존엔 비용 절감으로 비워둬 **①장애유형 입력이 없었음**. verdict 판정엔 무영향(정보 필드).
- **fix_results / 관측 status 캡처**(측정 스크립트): 원인 위치(file_path)와 golden 오라클 대조용 관측 status를 측정 아티팩트에 저장.

### (C) 측정 도구 (`scripts/metrics/`)
- `ground_truth.py`(golden+faults 로더) · `scoring.py`(산식) · `sut_control.py`(결함 구성 전환) · `run_measurement.py`(구성×N 실행→채점). 제품이 아니라 측정 전용 도구.

### (D) develop과의 관계
- develop 최신을 병합(우리 측정 거동 무변경 확인). develop의 신규(git-blame 담당자·Slack·CSV/PDF)는 측정 로직과 무관.
- 측정 전용 계측(`_api_error_code` 등)을 제품(develop)에 반영할지는 **측정 종료 후 별도 결정**.

## 3. 측정 방법 — 정답(ground truth)과 정확한 측정값

**정답 두 출처**: `golden/`(정상 동작 오라클 114케이스) · `faults/`(주입 결함 7개의 endpoint·장애유형·원인 위치).
**구성 매트릭스**: clean(결함 OFF) + 신뢰 결함 5종(RULE-001/002/003/004 + API-001) 각각 ON. 구성당 N회 반복(시드 고정).

| 지표 | 측정 방법 (정확한 값) |
|---|---|
| **유효 판정율** | `(PASS + 결함검출FAIL) / 전체 TC`. 보류(U)·검증미완(S) 제외. clean에서 산출. |
| **테스트 코드 정확도** | clean SUT는 전 케이스 통과가 정답 → `PASS / 전체`. **정정법**: 오라클이 명시(then status 보유)된 TC만 본 `accuracy_explicit` 도 병기(LLM 추정 오라클 노이즈 분리). |
| **결함 검출** | 결함 ON 시, clean에 없던 신규 `PRODUCT_DEFECT_CANDIDATE` FAIL이 해당 endpoint에서 나오나. **Recall = 검출 결함 / 주입 결함**, **Precision = 진짜 결함검출 / 전체 결함검출**(clean 오탐으로 보정). N회 **pass^k(일관성)** 병기. |
| **장애 분류** | 검출 결함에 대해 **①장애유형**(faults category: RULE→DOMAIN_RULE, API→API_ERROR…)과 **②결정분류**(PRODUCT_DEFECT_CANDIDATE 정분류) 각각 + **① ∧ ②**(둘 다 맞은 비율). |
| **원인 추론** | **(위치) Top-N**: 정답 fix_file이 fix_recommender 후보 Top-1/3/5에 드나 + **MRR**. **(의미)**: 후보 cause가 정답 원인과 의미 일치하나 → **LLM-judge** 0/1. |
| **시나리오 생성 정확도** | 생성 시나리오/TC를 golden과 매칭(req_id·endpoint·intent) → **TC·TS Recall/Precision** + **Requirement Coverage**. 실행 전 생성 단계 평가. |

**측정 환경(고정)**: 실행 SUT = 로컬 mini-bss-lite(게이트웨이 `localhost:8090`, DB 에이전트 `localhost:8091`),
service `sut-local-01`, target_root = system-under-test(codebase-index). DB 관측 100% 로컬.
**한계**: 단일 SUT — N회 반복은 표본 확대가 아닌 비결정성 안정화. 일반화는 "본 SUT 기준"으로 한정.

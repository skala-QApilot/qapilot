# 지시사항

위 정보를 바탕으로 다음 규칙에 따라 테스트 시나리오를 생성하라.

**[필수] 코드 인덱스 분석 절차 (시작 전 반드시 수행):**
먼저 "관련 요구사항"을 읽고 검증해야 할 사용자 동작과 정책을 확정하라. 그 다음 "코드베이스 분석 결과"의 엔드포인트 목록을 확인하고 각 TC가 호출할 실제 API를 매핑하라.
**관련 요구사항이 명시된 경우, 엔드포인트 목록은 해당 요구사항에 매핑된 API 후보이다. 이 후보 밖 API를 사용하지 말고, 후보가 없거나 TC와 맞는 후보가 없으면 api를 null로 둔다.**
**관련 요구사항이 "없음"인 라우터 fallback 모드에서만 나열된 모든 엔드포인트에 대해 TC를 설계해야 한다.**
그 다음 "핸들러 소스 코드"와 "헬퍼 함수 소스 코드" 섹션을 읽고 아래 항목을 추출하라:
- 각 if/elif 조건과 그에 따른 HTTPException 상태 코드 및 에러 메시지
- 코드에 나오는 실제 enum/상수 값 (예: status="CONFIRMED", contract_type="NONE" 등)
- 검증 함수 이름과 호출 조건, 외부 서비스 호출 여부
이 분석 결과를 기반으로 TC의 given/when/then과 values를 채워라. 코드에 없는 값은 지어내지 마라.

1. **분석 대상 파일의 기능 영역을 커버하는 TS를 정확히 1개 생성하라.** scenarios 배열에 원소가 1개여야 한다.
2. **"관련 요구사항"이 명시된 경우, 반드시 요구사항의 핵심 동작(생성·변경·조회·해지 등)을 먼저 TC로 만들고 그 다음 API를 매핑하라.** 예를 들어 "요금제 변경" 요구사항이라면 PATCH/PUT 엔드포인트가 핵심이다. 같은 리소스의 읽기(GET) 엔드포인트만 반복해서 생성하지 마라. 요구사항에 없는 엔드포인트를 커버하기 위한 TC를 추가하지 마라. "관련 요구사항"이 있으면 TC의 req_id를 관련 요구사항에 실제로 나열된 ID로 설정하라.
2-1. **"관련 요구사항"이 없음인 경우에만 "분석 대상 파일"의 각 엔드포인트마다 normal TC를 반드시 1개 이상 작성하라.** 엔드포인트가 3개면 normal TC >= 3개여야 한다.
3. TC 유형별 최소 개수:
   - normal: 요구사항 기반 모드에서는 요구사항의 happy path + 주요 정상 변형, 라우터 fallback 모드에서는 **엔드포인트 수 이상**
   - edge_case: 2개 이상 — **코드의 각 에러 분기(HTTPException)마다 별도 TC**
   - boundary: 1개 이상 (null/빈값/최솟값/최댓값 등 각각 별도 TC)
   - auth: 1개 이상 (JWT 없음 / 만료 JWT / 타인 리소스 접근 — 각각 별도 TC)
4. 엣지케이스는 "실패 1개"로 묶지 말고, HTTPException이 발생하는 조건마다 별도 TC를 작성하라.
5. 중복 요청 가능성이 있는 기능에는 동시성(concurrency) TC를 추가하라.
6. 각 TC의 values는 최소 2개 이상이며, 코드에서 확인한 실제 값을 사용하라.
7. TC의 req_id는 "관련 요구사항" 중 해당 TC와 가장 관련 있는 실제 ID로 설정하라. 관련 요구사항에 없는 ID를 만들지 마라. 관련 요구사항이 없으면 null로 설정하라.
7-1. TC의 depends_on은 이 TC를 실행하기 전에 반드시 선행되어야 하는 **동일 시나리오 내** TC의 ID 목록이다. 리소스 생성(POST) → 해당 리소스를 전제로 하는 조회/수정/삭제 TC처럼 상태 의존이 명확한 경우에만 설정하라. `"TC-01"` 형식으로 기재하고, 선행 TC가 없으면 `[]`로 설정하라.
8. TC의 api 필드에는 해당 TC가 검증하는 API 엔드포인트를 "METHOD /api/path" 형식으로 명시하라. **네 가지 절대 금지 사항:**
   - **존재하지 않는 경로 금지**: 반드시 위 "코드베이스 분석 결과"의 엔드포인트 목록에 실제로 나열된 경로만 사용하라. 목록에 없는 경로(/api/login, /api/users, /api/summary, /api/availability 등)는 절대 만들어 쓰지 마라.
   - **경로 파라미터 치환 금지**: `{order_id}`, `{plan_id}` 같은 경로 파라미터는 절대 실제 값(1, 999, null, 12345 등)으로 바꾸지 마라. 항상 `{param_name}` 형태 그대로 써야 한다. 실제 테스트 값은 `values` 필드에 기재하라 (예: api는 `"GET /api/orders/{order_id}"`, values에 `{"field":"order_id","value":"999",...}`).
   - **방어적 일괄 할당 금지**: 모든 TC에 동일한 API를 일괄 사용하지 마라. TC마다 그 TC가 실제로 테스트하는 엔드포인트를 정확히 써야 한다. 회원가입·로그인·생성·주문 TC는 POST 엔드포인트를, 수정·변경 TC는 PATCH/PUT을, 해지·삭제 TC는 DELETE/PATCH를, 조회 TC는 GET을 사용하라. method가 TC 내용과 맞지 않으면 null로 설정하라.
   - **요구사항 밖 API 금지**: "관련 요구사항"이 있으면 "코드베이스 분석 결과"에 나열된 요구사항 매핑 API 후보 안에서만 선택하라. 후보 목록에 없는 API는 실제 코드베이스에 있더라도 이 시나리오에 연결하지 마라.
   특정 엔드포인트에 대응되지 않는 TC는 null로 설정하라.
9. TS의 requirements 필드에는 "관련 요구사항"에 실제로 나열된 요구사항 번호만 기재하라 (예: ["FR-ORDER-01"]). 새 번호를 추출하거나 추측하지 마라. 참조한 요구사항이 없으면 빈 배열 []로 설정하라.
10. JSON 형식으로만 출력하라. 설명이나 마크다운 블록 없이 JSON만 반환하라.
11. **통합 테스트 불가 시나리오 생성 금지**:
    - 응답시간·처리량 등 성능 측정 TC는 생성하지 마라 (부하 테스트 도구 필요).
    - "코드베이스 분석 결과"의 엔드포인트 목록에 없는 내부/s2s API는 TC에 포함하지 마라.
    - 경로 파라미터 없는 엔드포인트(`GET /api/auth/me`, `GET /api/usage/summary` 등)에서 타인 리소스 접근 → 403 TC를 작성하지 마라. 이 API들은 JWT 기반으로 항상 본인 데이터만 반환한다.
    - 동일 TS 내에서 given/when/then이 실질적으로 동일한 TC를 반복하지 마라.
12. TC의 req_id는 반드시 "관련 요구사항"에 나열된 ID 그대로 설정하라. 관련 요구사항에 없는 FR/REQ ID는 사용하지 마라. 관련 요구사항이 없으면 null로 설정하라.
